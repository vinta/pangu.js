How the service worker, content script, and AI spacing talk

AI spacing is not a third context. It is one feature split across the two that exist: the content-script half flags candidates and applies late fixes, the service-worker half prompts the on-device model. The shape kind string and one message, CLASSIFY_CANDIDATES, join the halves.

One message enters the worker

CLASSIFY_CANDIDATES, sent by ai-spacing/content-script.ts over chrome.runtime.sendMessage. Nothing else messages the service worker.

The worker never messages the page

It only registers dist/content-script.js and dist/content-script.css with chrome.scripting. The popup is the only sender to the content script: PING and MANUAL_SPACING.

The content script is the gate

It reads is_ai_spacing_enabled once at init. The worker reads no settings for classification; it answers whatever arrives.

Only sentences cross

Candidates travel as { sentence, at }. Text nodes stay in the page, and labels come back zipped by index.

Why the model lives in the worker

LanguageModel.params and pinned sampling (temperature: 0, topK: 1) are available in extension contexts, not in the content script. Without them classification stays off rather than sampling freely (ADR 0017).

Worker lifetime costs a cold start

Chrome stops an idle service worker, and baseSessions and cachedAnswers die with it. The next CLASSIFY_CANDIDATES pays LanguageModel.create() again, which takes seconds. Warm-up (steps 9 to 12) exists for that.

The options page skips the worker

getModelAvailability() and downloadModel() run in options.ts and call LanguageModel directly. Model state is browser-wide, so the toggle can be on while the model is absent; pages then keep the rules output.
